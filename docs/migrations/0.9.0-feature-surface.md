# 0.9.0 — Feature surface collapse

## TL;DR

- Two GPU features only: **`gpu-cuda`** and **`gpu-metal`**.
- `gpu-coreml` users → switch to **`gpu-metal`** (now activates the CoreML EP automatically when ORT is in the build).
- ROCm / DirectML / OpenVINO / QNN / TensorRT / WebGPU users → use **`provider-onnx-dynamic`** + a vendor-supplied ORT build at runtime.
- Bump dependency declaration to `uni-xervo = "0.9"`.
- New default features: all three local backends (candle, mistralrs, onnx) **and** all remote providers (openai, gemini, vertexai, mistral, anthropic, voyageai, cohere, azure-openai). For a leaner build, use `default-features = false` and select explicitly.

## What changed

`uni-xervo` 0.7 / 0.8 exposed nine `gpu-*` features, each gated to a specific ONNX Runtime execution provider, with a build-time tarball fetcher (`build/ort_vendor.rs`) for the vendors pyke didn't ship. That surface produced three different ORT linking modes that had to be kept mutually exclusive in `build.rs` — useful but heavy.

0.9 collapses the matrix to:

| Feature | Effect |
|---|---|
| `provider-onnx` | Bundled ORT, statically linked. CPU EP. Default for most users who want ONNX. |
| `provider-onnx-dynamic` | `dlopen` ORT at runtime via `ORT_DYLIB_PATH`. BYO tarball. |
| `gpu-cuda` | Adds CUDA EP to ORT (when bundled) + CUDA kernels for candle/mistralrs. |
| `gpu-metal` | Adds CoreML EP to ORT (when bundled) + Metal kernels for candle/mistralrs. |

CPU is always available — there is no "CPU feature." GPU features are additive: at runtime, ORT registers the GPU EP first and silently falls back to CPU if the GPU path isn't available.

## Migration table

| Old feature | New path |
|---|---|
| `gpu-coreml` | `gpu-metal` (now bundles CoreML automatically when ORT is present) |
| `gpu-tensorrt` | `gpu-cuda` (the CUDA EP covers NVIDIA inference) |
| `gpu-directml` | `provider-onnx-dynamic` + Microsoft Windows GPU tarball |
| `gpu-rocm` | `provider-onnx-dynamic` + AMD `onnxruntime-rocm` package |
| `gpu-openvino` | `provider-onnx-dynamic` + Intel `openvino-onnxruntime` package |
| `gpu-qnn` | `provider-onnx-dynamic` + Microsoft Windows ARM64x tarball |
| `gpu-wgpu` | no replacement — open an issue if you need it |

### Catalog `execution_providers` strings

The recognized values are now `"cpu"`, `"cuda"`, `"coreml"`. Catalog entries using `"directml"`, `"rocm"`, `"openvino"`, `"qnn"`, `"tensorrt"` / `"nvrtx"`, or `"webgpu"` / `"wgpu"` will fail validation. If you were using `"coreml"` on macOS, you can keep the string verbatim — just compile with `gpu-metal` instead of `gpu-coreml`.

### Switching to `provider-onnx-dynamic` for a removed vendor

Example for AMD ROCm on Linux:

```toml
[dependencies]
uni-xervo = { version = "0.9", default-features = false, features = [
    "provider-onnx-dynamic",
    "provider-candle",
] }
```

At deploy time:

```sh
# Install AMD's onnxruntime-rocm package somewhere readable.
export ORT_DYLIB_PATH=/opt/onnxruntime-rocm/lib/libonnxruntime.so
./your-binary
```

`provider-onnx-dynamic` runs a fast preflight that returns a clear `RuntimeError::Config` if the dylib path is missing or unloadable, instead of hanging on the upstream ort 2.0.0-rc.12 OnceLock deadlock.

## What was removed

- Cargo features: `gpu-tensorrt`, `gpu-coreml`, `gpu-wgpu`, `gpu-directml`, `gpu-qnn`, `gpu-rocm`, `gpu-openvino`, internal `_ort-fetched-base`.
- `OnnxExecutionProvider` enum variants: `DirectMl`, `Rocm`, `OpenVino`, `Qnn`, `TensorRt`, `WebGpu`.
- `build/ort_vendor.rs` (Microsoft tarball fetcher) and the `UNI_XERVO_ORT_DIST_DIR` build-time override.
- Build-deps: `ureq`, `flate2`, `tar`, `zip`, `sha2`, `hex`.

## Why

The provider surface stabilized at two local backends (mistralrs + ONNX). Once that happened, the per-EP feature explosion was carrying weight that no real consumer needed — users pick *capability* (CPU vs GPU), not *which ONNX execution provider*. The escape hatch (`provider-onnx-dynamic`) covers the long tail of vendors. Future GPU backends will land as additional `gpu-*` features when concrete demand shows up.
