# Migrating to uni-xervo `0.5.6` — `provider-onnx` flips back to bundled CPU

**Audience:** anyone consuming uni-xervo `0.5.4` or `0.5.5` with `provider-onnx`, `provider-fastembed`, or any `gpu-*` feature.

## What changed (one-paragraph version)

`provider-onnx` no longer means "load-dynamic, you supply a tarball at runtime." It now means "bundled CPU, self-contained binary, no setup." If you want the load-dynamic deployment model, the new feature name is `provider-onnx-dynamic`. All `gpu-*` features now automatically imply `provider-onnx-dynamic` because pyke's bundled CPU lib (used by `provider-onnx`) doesn't contain GPU execution providers.

## Why we did this

`0.5.4` switched ort to `load-dynamic` to fix a silent-CPU-fallback bug for `gpu-cuda` users. That fix was correct, but it forced **every** `provider-onnx` user — including pure-CPU consumers who never wanted a GPU — to download a Microsoft ORT tarball and set `ORT_DYLIB_PATH` before any binary would run. That regression hit users who had been happily using uni-xervo as a single self-contained binary since the original release.

`0.5.6` restores the zero-config CPU experience as the default and exposes the load-dynamic flexibility under an explicit feature name. The two are mutually exclusive — you pick one based on your deployment model.

## Migration table

| Were on `0.5.5`'s | Switch to `0.5.6`'s | What you change |
|---|---|---|
| `provider-onnx` and need `ORT_DYLIB_PATH` to work | `provider-onnx-dynamic` | One feature name in `Cargo.toml`. Env var setup stays. |
| `provider-onnx` and want bundled CPU | `provider-onnx` | Nothing in `Cargo.toml`. **Remove** `ORT_DYLIB_PATH` from deploy scripts; binary is now self-contained. |
| `gpu-cuda` (any other GPU feature) | `gpu-cuda` (same other feature) | Nothing — `gpu-cuda` now auto-implies `provider-onnx-dynamic`. Continue setting `ORT_DYLIB_PATH` to a CUDA-flavored ORT tarball. |
| Bundled binary that I never realized was load-dynamic | `provider-onnx` | If your binary "just worked" before, the move to `0.5.6`'s `provider-onnx` (bundled) gets you back to that experience. |

## Cargo.toml diffs

### Pure CPU, want zero runtime config

**Before** (`0.5.4` / `0.5.5`):
```toml
uni-xervo = { version = "0.5.5", features = ["provider-onnx"] }
```
Plus a deploy step that sets `ORT_DYLIB_PATH` to a downloaded ORT tarball.

**After** (`0.5.6`):
```toml
uni-xervo = { version = "0.5.6", features = ["provider-onnx"] }
```
**Remove** the `ORT_DYLIB_PATH` setup from your deploy. Build host needs network on first build (pulls libonnxruntime.a from pyke's CDN, ~30 MB). All subsequent builds offline.

### Want load-dynamic flexibility (e.g. you swap tarballs across vendors)

**Before**:
```toml
uni-xervo = { version = "0.5.5", features = ["provider-onnx"] }
```

**After**:
```toml
uni-xervo = { version = "0.5.6", features = ["provider-onnx-dynamic"] }
```
Continue setting `ORT_DYLIB_PATH`. No other changes.

### Need CUDA / ROCm / DirectML / etc.

**Before** (`0.5.5`):
```toml
uni-xervo = { version = "0.5.5", features = ["gpu-cuda"] }
```

**After** (`0.5.6`):
```toml
uni-xervo = { version = "0.5.6", features = ["gpu-cuda"] }
```
**No change.** `gpu-cuda` now implies `provider-onnx-dynamic` automatically. Continue setting `ORT_DYLIB_PATH` to a CUDA-flavored Microsoft ORT tarball.

## Common errors after migration

### `Features 'provider-onnx' and 'provider-onnx-dynamic' are mutually exclusive`

You activated both features. Most common cause: you have `provider-onnx` AND a `gpu-*` feature, since the GPU feature now implies `provider-onnx-dynamic`. Fix: drop `provider-onnx` from your feature list — `gpu-cuda` (or whichever) brings `provider-onnx-dynamic` along automatically.

### `cannot load ONNX Runtime dynamic library 'libonnxruntime.so'`

Under `provider-onnx-dynamic` (or any `gpu-*`) without `ORT_DYLIB_PATH` set. Same error message as in `0.5.5`. The fix is the same: set `ORT_DYLIB_PATH` to your ORT tarball, or switch to bundled `provider-onnx` if you only need CPU.

### Build is now slow / first build downloads ~30 MB

That's expected under `provider-onnx`. The bundled CPU library is fetched from pyke's CDN on first build and cached at `~/.cache/ort.pyke.io/`. Subsequent builds reuse the cache. CIs that block network egress need to either allow it or pre-populate the cache (or set `ORT_LIB_LOCATION=/path/to/libonnxruntime.a`).

### Binary is ~70 MB larger

Also expected — that's the bundled `libonnxruntime.a` after static-link dead-code elimination. If binary size matters, switch to `provider-onnx-dynamic` and ship the ORT tarball alongside the binary as a separate file.

## Deployment models — quick decision tree

- **CLI tool / single binary distribution, CPU only** → `provider-onnx`. Zero config.
- **Server with NVIDIA GPU** → `gpu-cuda` + ship the ORT GPU tarball alongside.
- **Cross-vendor server (NVIDIA + AMD + Apple)** → `provider-onnx-dynamic` + per-host ORT tarball selection.
- **Embedded device, no GPU** → `provider-onnx`.
- **Apple Silicon, want Core ML / ANE** → `gpu-coreml` + macOS ORT tarball.

## Build-host requirements per mode

| Mode | Build host needs | Runtime needs |
|---|---|---|
| `provider-onnx` (bundled) | Network access to pyke's CDN on first build | Nothing (lib is in the binary) |
| `provider-onnx-dynamic` | Nothing | `ORT_DYLIB_PATH` set to the right tarball |
| `gpu-cuda` | nvcc + matching driver + `CUDA_COMPUTE_CAP` (for candle/mistralrs PTX) | NVIDIA driver + CUDA-flavored ORT tarball |
| `gpu-metal` (Apple) | Xcode CLT (for candle/mistralrs MSL) | Nothing extra (Metal is in the OS) |

Once you understand the deployment model you're targeting, the cargo features are straightforward — pick exactly one of `provider-onnx`, `provider-onnx-dynamic`, or a `gpu-*`. The `build.rs` guard catches the most common misconfigurations at compile time.
