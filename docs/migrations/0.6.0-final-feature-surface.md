# Migrating to uni-xervo `0.6.0` — final ONNX/GPU feature surface

**Audience:** anyone consuming uni-xervo `0.5.x`. This is the final, settled feature shape — no more iterative migrations.

## TL;DR

`0.6.0` makes every `gpu-*` feature **bundle its ONNX Runtime automatically at build time**. No `ORT_DYLIB_PATH` setup at runtime for any vendor that has a prebuilt distribution. Pick exactly one of:

```
provider-onnx          # CPU bundled, self-contained binary
gpu-cuda               # NVIDIA, bundled (pyke), self-contained
gpu-tensorrt           # NVIDIA TensorRT-RTX, bundled (pyke), self-contained
gpu-coreml             # Apple GPU+ANE, bundled (pyke macOS), self-contained
gpu-wgpu               # Vendor-neutral via WebGPU, bundled (pyke), self-contained
gpu-directml           # Windows any-vendor GPU, bundled (Microsoft), self-contained
gpu-qnn                # Snapdragon X NPU, bundled (Microsoft), self-contained
gpu-rocm               # AMD on Linux — NO prebuilt; needs provider-onnx-dynamic + AMD's rocm-onnxruntime
gpu-openvino           # Intel — NO prebuilt; needs provider-onnx-dynamic + Intel's openvino-onnxruntime
provider-onnx-dynamic  # Power-user escape: BYO ONNX Runtime via ORT_DYLIB_PATH
gpu-metal              # Apple Metal (orthogonal to ort path; candle/mistralrs only)
```

Mutually exclusive: `build.rs` panics if you combine modes. The error message tells you which features conflict.

## Migration table

| Were on `0.5.x` with… | Switch to `0.6.0`'s | What changes |
|---|---|---|
| `provider-onnx` (need ORT_DYLIB_PATH) | `provider-onnx` | Now bundles CPU automatically. **Remove `ORT_DYLIB_PATH` from your deploy** — binary is self-contained. |
| `provider-onnx` (already bundled in `0.5.6`) | `provider-onnx` | No change in behavior; this is the same path as `0.5.6`. |
| `provider-onnx-dynamic` | `provider-onnx-dynamic` | Same: power-user escape, BYO tarball. Unchanged. |
| `gpu-cuda` | `gpu-cuda` | Now bundles automatically. **Remove `ORT_DYLIB_PATH`** — pyke fetches CUDA EP at build, sidecars stage in `target/<profile>/`. Note: cuDNN is still a host requirement (it's an NVIDIA driver-layer thing; we don't bundle vendor drivers). |
| `gpu-coreml` | `gpu-coreml` | Now bundled via pyke's macOS build. Apple Neural Engine works without setup. |
| `gpu-directml` | `gpu-directml` | Now bundled via Microsoft's Windows GPU tarball. build.rs fetches at build time. |
| `gpu-rocm` | `gpu-rocm` + `provider-onnx-dynamic` | AMD is the only vendor without a central prebuilt. build.rs warns and you supply AMD's ORT build at deploy via `ORT_DYLIB_PATH`. |
| `gpu-openvino` | `gpu-openvino` + `provider-onnx-dynamic` | Same situation as rocm — Intel ships separately. |

Common case for migration: **change nothing in your `Cargo.toml`, just remove the `ORT_DYLIB_PATH` setup from your deploy scripts**.

## Build host requirements

| Feature | Build host needs | Runtime host needs |
|---|---|---|
| `provider-onnx` | network on first build (pyke CDN) | nothing |
| `gpu-cuda` / `gpu-tensorrt` | network + nvcc + `CUDA_COMPUTE_CAP` (for candle/mistralrs PTX) | NVIDIA driver + cuDNN |
| `gpu-coreml` | macOS toolchain | macOS Metal + ANE (part of OS) |
| `gpu-wgpu` | network on first build | Vulkan / DX12 driver (any GPU vendor) |
| `gpu-directml` | network on first build | Windows 10+ |
| `gpu-qnn` | network on first build | Windows ARM64 with QNN runtime |
| `gpu-rocm` | nothing | AMD driver + ROCm + AMD's onnxruntime-rocm package + `ORT_DYLIB_PATH` |
| `gpu-openvino` | nothing | Intel OpenVINO runtime + `ORT_DYLIB_PATH` |
| `provider-onnx-dynamic` | nothing | any ORT shared library on disk + `ORT_DYLIB_PATH` |
| `gpu-metal` | macOS + Xcode CLT | nothing extra (Metal in OS) |

## Build-time `CUDA_COMPUTE_CAP`

For `gpu-cuda` / `gpu-tensorrt`, candle and mistralrs compile their own CUDA kernels with `nvcc` at build time. To avoid the PTX-version trap (where build-host `nvcc` is newer than runtime driver) **set `CUDA_COMPUTE_CAP` to your target GPU's compute capability**:

```sh
# Find your GPU's compute capability
nvidia-smi --query-gpu=compute_cap --format=csv,noheader
# 8.9   ← RTX 4070 / 4080 / 4090
# 8.0   ← A100
# 9.0   ← H100

# Build for that exact capability (no PTX, just SASS)
CUDA_COMPUTE_CAP=89 cargo build --features gpu-cuda
```

If unset, candle's `bindgen_cuda` shells out to `nvidia-smi` on the build host — works on a developer box, fails on GPU-less CI. Pin it in CI to whatever the deployment hosts use.

## What the bundled artifact looks like

For `provider-onnx` (CPU):
```
target/release/your-binary       # ~70 MB extra from statically linked libonnxruntime.a
```
One file. Ship it. Done.

For `gpu-cuda` and the other "bundled" GPU features:
```
target/release/your-binary
target/release/libonnxruntime_providers_cuda.so       (≈30 MB)
target/release/libonnxruntime_providers_shared.so     (≈100 KB)
target/release/libonnxruntime_providers_tensorrt.so   (also bundled when ort/cuda)
```
Binary plus a few sidecar `.so` files. The binary's rpath is `$ORIGIN`, so as long as the sidecars travel alongside the binary in the same directory, deployment is just "copy the directory."

If you `cargo install`, the sidecars don't get copied to `~/.cargo/bin/`. You need them present at runtime — copy them manually or use `LD_LIBRARY_PATH` to point at `target/<profile>/`. (A future `uni-xervo-bundle` helper will automate this.)

## Why `gpu-rocm` and `gpu-openvino` aren't bundled

Neither pyke (the ort-rs upstream maintainer) nor Microsoft (the ONNX Runtime project owner) distribute a prebuilt ONNX Runtime tarball for these vendors:

- **AMD ROCm**: AMD distributes `onnxruntime-rocm` themselves through `repo.radeon.com`. Their build is tightly coupled to specific ROCm versions and Linux kernel modules; they don't publish a "drop-in" tarball that bundles cleanly.
- **Intel OpenVINO**: Intel ships `openvino-onnxruntime` separately through their own channels. Same situation.

Bundling these would mean uni-xervo maintaining build-script logic for distributions that move, version on independent cadences, and target very specific hardware/kernel combinations. Out of scope.

The migration: keep using the `gpu-rocm` / `gpu-openvino` cargo feature (it compiles in the right Rust EP type), but pair it with `provider-onnx-dynamic` and supply the vendor's runtime at deploy via `ORT_DYLIB_PATH`. `build.rs` emits a `cargo:warning=` reminder during build.

## Deployment cheatsheet

### Single-binary deployment (CPU only)
```toml
features = ["provider-onnx"]
```
Build artifact is one file. Ship it.

### NVIDIA GPU server (Linux)
```toml
features = ["gpu-cuda"]
```
`cargo build --features gpu-cuda` with `CUDA_COMPUTE_CAP=<your_cap>`. Deploy: copy `target/release/your-binary` plus the `.so` files in `target/release/` to the host. NVIDIA driver + cuDNN must be installed on the host (typically already present).

### Apple Silicon (macOS / iOS)
```toml
features = ["gpu-coreml", "gpu-metal"]   # Core ML EP for ort + Metal kernels for candle/mistralrs
```
Single binary. Ship it. macOS provides everything else.

### Windows (any GPU vendor)
```toml
features = ["gpu-directml"]
```
First build pulls Microsoft's Windows GPU tarball (~300 MB). DirectML works on NVIDIA, AMD, Intel Arc, Snapdragon Adreno on Windows.

### Multi-GPU embedded device (Snapdragon X laptop)
```toml
features = ["gpu-directml", "gpu-qnn"]   # GPU via DirectML, NPU via QNN
```
Wait, no — these are mutually exclusive (different ort linking semantics). Pick one based on your priority. Most apps use DirectML; QNN is for NPU-aware models.

## Common errors

### `Multiple mutually-exclusive ONNX linking modes are active simultaneously`
You combined a "Mode B" GPU feature (gpu-cuda, gpu-tensorrt, gpu-coreml, gpu-wgpu) with a "Mode C" (gpu-rocm, gpu-coreml, gpu-directml, gpu-openvino, gpu-qnn). Pick one.

### `cannot load ONNX Runtime dynamic library 'libonnxruntime.so'`
Means you're in `provider-onnx-dynamic` mode (or used `gpu-rocm` / `gpu-openvino`) and didn't set `ORT_DYLIB_PATH`. Set it to the vendor's `libonnxruntime.so`.

### `libcudnn.so.9: cannot open shared object file`
You enabled `gpu-cuda` but cuDNN isn't on the loader path. Install cuDNN (it ships with the CUDA Toolkit) or add its directory to `LD_LIBRARY_PATH`. Typical path: `/usr/local/cuda-*/targets/x86_64-linux/lib/`.

### `CUDA_ERROR_UNSUPPORTED_PTX_VERSION`
Your build-host `nvcc` is newer than the runtime driver. Set `CUDA_COMPUTE_CAP` to your runtime GPU's compute cap so the build emits SASS only and skips PTX. See the "Build-time CUDA_COMPUTE_CAP" section above.

### `gpu-rocm` warns at build but I want it to "just work"
ROCm isn't bundleable from a central prebuilt. Add `provider-onnx-dynamic` to your features (or use `gpu-rocm` alone, which auto-implies the load-dynamic mode internally), build AMD's `onnxruntime-rocm` package, and set `ORT_DYLIB_PATH` to its `libonnxruntime.so` at deploy time.
