# Migrating to uni-xervo `0.7.0` — unified ONNX provider

**Audience:** anyone consuming uni-xervo `0.6.x` who registered or referenced the cross-encoder reranker via `LocalOnnxRerankerProvider` or the `local/onnx-reranker` provider id.

## TL;DR

The two ONNX providers are now one. Cross-encoder reranking is a task on `LocalOnnxProvider`, not its own provider:

| Before (`0.6.x`) | After (`0.7.0`) |
|---|---|
| `LocalOnnxProvider` — capability `[Raw]`, id `local/onnx` | `LocalOnnxProvider` — capabilities `[Raw, Rerank]`, id `local/onnx` |
| `LocalOnnxRerankerProvider` — capability `[Rerank]`, id `local/onnx-reranker` | **Removed.** Use `LocalOnnxProvider` for both tasks. |

This aligns the ONNX backend with the rest of the provider matrix (`cohere` covers `[Embed, Rerank, Generate]`; `mistralrs` covers `[Embed, Generate]`). Each backend gets one provider; the task is selected per spec.

## Migration steps

### 1. Drop the second registration

```rust
// Before
runtime_builder
    .register_provider(LocalOnnxProvider::new())
    .register_provider(LocalOnnxRerankerProvider);

// After
runtime_builder
    .register_provider(LocalOnnxProvider::new());
```

`LocalOnnxProvider::new()` now declares both `Raw` and `Rerank` in its capabilities and dispatches inside `load()` based on `spec.task`.

### 2. Update catalog specs

```diff
 ModelAliasSpec {
     alias: "rerank/minilm".to_string(),
     task: ModelTask::Rerank,
-    provider_id: "local/onnx-reranker".to_string(),
+    provider_id: "local/onnx".to_string(),
     model_id: "cross-encoder/ms-marco-MiniLM-L6-v2".to_string(),
     ...
 }
```

The `task: Rerank` field already routes correctly to the cross-encoder code path inside the unified provider.

### 3. Remove `LocalOnnxRerankerProvider` imports

```diff
- use uni_xervo::provider::LocalOnnxRerankerProvider;
+ use uni_xervo::provider::LocalOnnxProvider;
```

The type and the `local/onnx-reranker` provider id no longer exist. There is no deprecated alias — clean break.

### 4. Rename `OnnxRunner` → `RawTensorModel`

The trait, runtime accessor, instrumented wrapper, and mock all renamed to drop the framework-specific name. The signatures and behavior are byte-identical.

```diff
- use uni_xervo::traits::OnnxRunner;
+ use uni_xervo::traits::RawTensorModel;

- let runner = runtime.onnx_runner("raw/foo").await?;
+ let runner = runtime.raw_tensor_model("raw/foo").await?;
```

Renames applied:

| Before | After |
|---|---|
| `traits::OnnxRunner` | `traits::RawTensorModel` |
| `runtime.onnx_runner(alias)` | `runtime.raw_tensor_model(alias)` |
| `reliability::InstrumentedOnnxRunner` | `reliability::InstrumentedRawTensorModel` |
| `mock::MockOnnxRunner` | `mock::MockRawTensorModel` |
| file `src/traits/onnx_runner.rs` | file `src/traits/raw_tensor_model.rs` |

The motivation: the other three task traits (`EmbeddingModel`, `RerankerModel`, `GeneratorModel`) describe *semantic capabilities* — embed text, score documents, generate text — and any provider can fulfill them. `OnnxRunner` named the *transport* (ONNX), not a capability, and made no semantic promise. Renaming to `RawTensorModel` aligns the name with what it actually is (raw tensor I/O) and matches the `*Model` suffix used by the other task traits. The asymmetry that `Raw` is a framework-direct escape hatch rather than a semantic task remains; that's an architectural question for a future PR (see [`docs/proposals/provider-task-roadmap.md`](../proposals/provider-task-roadmap.md)).

`ModelTask::Raw` is **not** renamed — the task variant in catalog specs (`task: "Raw"`) is unchanged.

## What didn't change

- The trait shape (`run`, `run_batch`, `input_signature`, `output_signature`, `max_batch_size`, `active_execution_providers`) is identical between `OnnxRunner` and `RawTensorModel`. The rename is purely cosmetic.
- Public traits `RerankerModel`, `EmbeddingModel`, `GeneratorModel`, `ModelProvider` are unchanged.
- The model catalog format is unchanged apart from the `provider_id` rename.
- ONNX Runtime feature gating, GPU execution-provider selection (`provider-onnx`, `gpu-cuda`, …) are all carried over from `0.6.0` unchanged. See [`0.6.0-final-feature-surface.md`](0.6.0-final-feature-surface.md) for that surface.
- Cross-encoder rerank semantics (raw-logit output, sigmoid normalization in the caller) are unchanged. See [`docs/proposals/onnx-reranker-followups.md`](../proposals/onnx-reranker-followups.md) for outstanding follow-ups (score normalization API, etc.) — paths in that doc that reference `local_onnx_reranker.rs` should be read as `local_onnx/rerank.rs`.

## File-layout change (informational)

The implementation moved to a sibling-file module to match the `traits.rs` + `traits/raw_tensor_model.rs` precedent:

```
src/provider/local_onnx.rs           — unified provider entry (capabilities + load() dispatch)
src/provider/local_onnx/raw.rs       — raw tensor execution task
src/provider/local_onnx/rerank.rs    — cross-encoder rerank task
```

This is a private detail — public API references continue to be `uni_xervo::provider::LocalOnnxProvider`. No `pub use` paths changed for the surviving type.

## Why now

The unified shape is the design intent of uni-xervo (one provider per backend, multiple tasks per provider) and is what every other provider follows. The split was a historical artifact of how `LocalOnnxRerankerProvider` got hoisted into uni-xervo from uni-db in `0.5.2`. Fixing it before Phase 1 of the [provider × task roadmap](../proposals/provider-task-roadmap.md) (dense embed, sparse embed, image embed on the same backend) prevents three more incorrect provider IDs from being entrenched.
