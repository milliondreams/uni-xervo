# Migrating to uni-xervo `0.5.4` — `ort` switched to `load-dynamic`

**Audience:** anyone consuming uni-xervo `0.5.x` who has `provider-onnx`, `provider-fastembed`, or any of the `gpu-*` features enabled.

## What changed

In `0.5.4` we switched the `ort` crate from `download-binaries` (which bundles a CPU-only ONNX Runtime static library) to `load-dynamic` (which expects the ONNX Runtime to be present on disk at runtime). This is what enables the runtime-selectable execution-provider model documented in [`docs/proposals/gpu-runtime-architecture.md`](../proposals/gpu-runtime-architecture.md).

**The headline impact:** any test or binary that creates an ORT-backed session (via `LocalOnnxProvider`, `LocalOnnxRerankerProvider`, or `LocalFastEmbedProvider`) now needs an ONNX Runtime shared library on disk plus `ORT_DYLIB_PATH` (or a system loader path) pointing at it.

## Migration steps

### 1. Update your `Cargo.toml`

If your crate **also** depends on `ort` directly (alongside `uni-xervo`), update its features:

```diff
-ort = { version = "=2.0.0-rc.12", default-features = false,
-        features = ["download-binaries", "ndarray"], optional = true }
+ort = { version = "=2.0.0-rc.12", default-features = false,
+        features = ["load-dynamic", "ndarray", "api-24"], optional = true }
```

Cargo unifies features across the dep graph, so leaving one consumer on `download-binaries` while another uses `load-dynamic` puts ort in an undefined state. **All consumers in the workspace must agree.**

### 2. Pick an ONNX Runtime release

Microsoft publishes pre-built tarballs at <https://github.com/microsoft/onnxruntime/releases>. Match the artifact to your hardware:

| Target | Tarball |
|---|---|
| Linux x64, CPU only | `onnxruntime-linux-x64-1.20.1.tgz` |
| Linux x64, NVIDIA | `onnxruntime-linux-x64-gpu-1.20.1.tgz` |
| Linux x64, AMD | `onnxruntime-linux-x64-rocm-1.20.1.tgz` |
| Linux ARM64 (Jetson, Pi) | `onnxruntime-linux-aarch64-1.20.1.tgz` |
| macOS Apple Silicon | `onnxruntime-osx-arm64-1.20.1.tgz` |
| macOS Intel | `onnxruntime-osx-x86_64-1.20.1.tgz` |
| Windows x64, GPU | `onnxruntime-win-x64-gpu-1.20.1.zip` |
| Windows x64, CPU | `onnxruntime-win-x64-1.20.1.zip` |
| iOS | `onnxruntime-ios-1.20.1.tgz` |

ORT version `1.20.1` matches the ABI expected by `ort = "=2.0.0-rc.12"`. Check ort-rs release notes if you're using a different rc.

### 3. Set `ORT_DYLIB_PATH` before any ORT-backed session is created

```sh
# Linux / macOS
curl -LO https://github.com/microsoft/onnxruntime/releases/download/v1.20.1/onnxruntime-linux-x64-1.20.1.tgz
tar xzf onnxruntime-linux-x64-1.20.1.tgz
export ORT_DYLIB_PATH=$PWD/onnxruntime-linux-x64-1.20.1/lib/libonnxruntime.so

# Windows
# Unzip onnxruntime-win-x64-1.20.1.zip, then either set ORT_DYLIB_PATH
# or copy onnxruntime.dll alongside your binary.
$Env:ORT_DYLIB_PATH = "$PWD\onnxruntime-win-x64-1.20.1\lib\onnxruntime.dll"
```

For CI, do this in your workflow before `cargo nextest run`. For deployed binaries, document this in your install instructions or set it in a service unit / launchd plist.

### 4. (Optional) request specific execution providers

The default ORT EP list is feature-aware: `[cuda, cpu]` if `gpu-cuda` is on, `[cpu]` otherwise. To request a different list per-model, set `execution_providers` in the catalog spec options:

```json
{
  "options": {
    "execution_providers": ["coreml", "cpu"]
  }
}
```

Accepted: `cpu`, `cuda`, `coreml`, `directml`. Unknown values fall back to `cpu`.

## What didn't change

- **Public API surface** — the `LocalOnnxProvider` / `LocalOnnxRerankerProvider` / `LocalFastEmbedProvider` types, methods, and trait implementations are unchanged.
- **Catalog spec format** — same JSON, same fields. The `execution_providers` option already existed; it's now load-bearing.
- **Behavior on hosts that already have system ORT installed** (Linux distros that package `libonnxruntime.so`, macOS with brew-installed onnxruntime, etc.) — the dynamic loader finds it via standard `LD_LIBRARY_PATH` / `DYLD_LIBRARY_PATH` paths. No `ORT_DYLIB_PATH` needed in that case.

## Common errors after migration

### `Failed to load library libonnxruntime_providers_shared.so`

The ORT tarball you're using is the *CPU* build, but the session requested a GPU EP. Either:
- Switch to the GPU-flavored tarball for your vendor (`-gpu-` in the filename), or
- Remove the GPU EP from the request list (or accept the silent fallback to CPU).

### `Failed to load library: cannot open shared object file`

`ORT_DYLIB_PATH` isn't set, or points at a non-existent file. The error message includes the path — verify the file exists and is readable.

### `error: failed to select a version for the requirement ort = ...`

You have a `ort = { features = ["download-binaries"] }` somewhere in your workspace alongside `uni-xervo`'s `load-dynamic`. Find it (likely your top-level Cargo.toml or a sibling crate) and update per step 1.

## Rollback

If you need to stay on the old behavior temporarily, pin uni-xervo to `0.5.3`:

```toml
uni-xervo = { version = "=0.5.3", default-features = false }
```

Note that `0.5.3` still has the silent-CPU-fallback bug for `gpu-cuda` users — you trade the migration cost for the bug.

## Future-proofing

When ORT 2.0 stabilizes `Session::providers()` (currently not exposed in the Rust binding), `active_execution_providers()` will report *attached* EPs instead of *requested* ones. No code changes required on your end at that point; the method semantics improve transparently.
